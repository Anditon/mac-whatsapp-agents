Case study · Application for AI Engineer, Agents · Anton, based in Milan

A WhatsApp front desk for a gym, with two Claude agents in it

Since February 2026 I have designed, built and run, on my own, the messaging system of MAC SportsClub in Maastricht: a gym with two buildings and about 1,300 active members. It replies to new leads within minutes, follows up trial classes, nudges members who stop coming, offers upgrades, and passes anything uncertain to the front desk. Two parts run on Claude: a classifier that routes every website trial request, and a WhatsApp assistant that drafts answers for staff to approve.

Code: github.com/Anditon/mac-whatsapp-agents. Every figure here comes from the live system. Member data never appears; the inbox screenshot uses made-up conversations. I can show the live system and walk through the code in a call.

How the system fits together

Everything runs on a self-hosted n8n server. Most of the logic is JavaScript inside n8n Code nodes, because long chains of low-code nodes made bugs hard to see. The member system (Virtuagym) is the source of truth for members, check-ins, classes and invoices. Airtable holds contacts, conversations, messages and settings. A custom inbox lets the front desk read every thread, approve the assistant's drafts and send templates.

Live today: lead intake (forms and QR), trial follow-up, inactivity nudge, upsell, plan upgrade, nightly booking reconcile, three data syncs, inbound WhatsApp with the assistant, the inbox and its API, payment reminders in dry run, a daily health check and a weekly report.

The front-desk inbox

Meta's own inbox doesn't work with Cloud API numbers, so I built one: a single HTML and JavaScript page with hand-written CSS, backed by an n8n API. Staff see every conversation, including the automated ones, and this is where the assistant's drafts wait for a person.

What happens to a member, and when

Each stage of a member's life has its own automation. Once someone gives notice, every offer and nudge stops.

Lead

Trial

  • Day 1 and Day 3 follow-ups, each after a live check
  • Attendance follow-up at 11:30
  • Nightly booking check, so nobody who booked is asked again

Member

  • Upsell for members who train often

At every stage the front desk sees the conversation in the inbox, and the assistant can answer questions (today only for my test number).
Agent 1

The trial classifier

Live on every website trial requestClaude Haiku 4.5

When someone books a trial on the website, the form arrives as an e-mail with a free-text message. The classifier reads it and picks the first WhatsApp message they get, out of four paths.

AGeneral welcomeNo class named, or a very short message.
BNamed classThe reply names the class they asked for.
RReformer PilatesA separately paid module, so the reply states the price instead of promising a free trial.
CA person repliesA real question, or more than one class. A template can only name one, and answering half a request reads as not listening.

What went wrong

In September the club told me someone who asked for Reformer Pilates had been answered about Aerial Yoga. The class list in the prompt had no Reformer entry, so the model picked the closest class it knew. All 10 Reformer requests since July were wrong. Eight people were told their Pilates trial was reserved, for a class that costs money and isn't in any membership.

While fixing it, I found that path C had never worked. Its code used fetch, which doesn't exist in n8n's sandbox, so it failed on every call. 14 of the 19 people ever sent to "a person replies" got no message and no flag in the inbox.

How I checked the fix

I replayed all 75 real trial messages through the old and the new prompt, with the production model and credential, in a throwaway workflow. 24 classifications changed, and I read every one: 8 Reformer requests moved to R, 2 multi-class requests moved to a person, and 12 general gym requests moved out of the broken path C to a welcome. The hard cases:

MessagePathWhy
"former pilates"RA typo for Reformer.
"pilates of yoga"BDutch "of" means "or": one class, either is fine.
"mac Power (Full Body Barbell workout)"BOne class with a long name, not two classes.
What I took from it

A classifier with a closed list fails silently and confidently on anything missing from the list. I now check the list against the live source and replay the real message history, old prompt against new, before I ship a prompt change. I also test the hand-over path as hard as the happy path, because that is where this one was broken.

Agent 2

The WhatsApp assistant

Built and tested · answers only my test numberClaude Sonnet 4.6

It answers questions about opening hours, prices, classes, trials and cancelling, using a staff-editable FAQ and the live timetable, and hands everything else to a person. It runs inside the inbound WhatsApp webhook as three nodes: a gate, the Claude call, and a decide-and-act step. I tuned the prompt first in a local harness that mirrors those nodes, then ported it.

The gate runs before any API call: on/off switch, do-not-contact, a staff member has claimed the thread, our own number, non-text message, opt-out keyword, empty message, a repeat delivery from Meta, and a 20-second rate cap. The Claude call sends a cached system prompt (identity, tone, FAQ, rules), a small uncached context block, and the thread as alternating turns.

// Bot Decide + Act (n8n Code node, production)
// A max_tokens cut-off returns a PARTIAL tool input (e.g. only {decision:'reply'}),
// which would otherwise read as confidence 0 and escalate with a blank reason.
if (resp.stop_reason === 'max_tokens') throw new Error('truncated_max_tokens');
const tu = (resp.content || []).find((b) => b.type === 'tool_use' && b.name === 'emit_reply');
if (!tu || !tu.input) throw new Error('no_tool_use');
// ...any throw above becomes { decision: 'escalate', reason: 'bot_error: ...' }

let decision = parsed.decision === 'reply' ? 'reply' : 'escalate';
confidence = Math.max(0, Math.min(1, Number(parsed.confidence) || 0));
if (decision === 'reply' && confidence < CONF_THRESHOLD) decision = 'escalate';  // 0.75, staff-set
if (decision === 'reply' && !String(parsed.reply || '').trim()) decision = 'escalate';

Lightly shortened from the deployed node. The model's output is never trusted to be complete: every path that isn't a clean, confident reply ends with a person.

Prompt and knowledge

Only answer from the facts above. If the answer is not clearly in those facts, do NOT guess, invent, estimate, or reason your way to an answer. Escalate to a human instead. A wrong confident answer is far worse than handing it to a person.

Always escalate, however it's phrased:

  1. Anything not in the facts.
  2. Personal training or nutrition coaching specifics.
  3. Money and plan changes: refunds, billing disputes, switching, freezing. The plain "how do I cancel?" procedure is answered directly.
  4. Anything medical: injuries, pregnancy, conditions.
  5. Complaints or upset messages.
  6. Confirming a specific booked slot.
  7. A request for a person, or "is this a bot?".
  • Grounded in what staff actually say. A script pulled 101 question-and-answer pairs out of real front-desk replies. Six facts in the FAQ were missing or wrong. The FAQ said the trial was free; it costs €14.50, which comes off the first invoice if you sign up that day.
  • Live timetable. A job at 06:00 reads the week's classes from the member system and stores a clean timetable the prompt includes. The events endpoint's cursor tracks edits, not dates, and a short one silently dropped half the week's classes. A review caught that before launch.
  • Staff own the knowledge. FAQ, tone, mode, threshold and the on/off switch live in a settings row edited from the inbox. The editor filters prompt-injection attempts: override phrasing, fake section headers, role tags, the tool's name.
  • Minimal data. The model sees today's date, a first name, language, CRM status and membership type. No e-mail, phone number or IDs. The big static prefix is cached.

Why it isn't answering customers yet

The club hasn't signed a data processing agreement that covers the model provider, and its privacy notice doesn't mention AI yet. Until both are done, the gate only lets my own number through. Switching it on is a one-line change, and I am keeping it closed on purpose. The case for opening it is in the data: in an August sample, 26 of 45 recent customer threads ended without an answer. The plan is draft mode first, so staff approve every reply before anything goes out on its own.

Sending to real people

Most messages come from scheduled automations on Meta-approved templates. They reach real people every day, so a large part of the work was the rules around each send. Each rule below came from a real incident.

A member who had given notice was offered a 52-week plan four days before their contract ended. In the member system, "active" stays true for the whole notice period.

RuleEvery member-facing send checks notice given, contract end and contract start. A back-check found five such sends. The upgrade pool fell from 72 to 40, because the longest-standing members are also the likeliest to be leaving.

Two people who had just signed up got "how was your trial?" and a sign-up offer, because the CRM still listed them as leads.

RuleEvery lead follow-up asks the member system live, just before sending, and sends nothing if it can't get an answer.

Inactivity was judged on card check-ins. 171 people who train in classes never swipe a card, and 30 weekly class-goers were about to get "we miss you".

RuleA class attendance sync, and inactivity uses whichever came last: a check-in or a class.

Delivery receipts were ignored. In 14 days, 43 messages never arrived, and the inbox showed them as sent.

RuleSent, delivered, read and failed are recorded per message and shown in the inbox. Known-bad numbers are never messaged again.

Numbers copied from a phone's contact card carry invisible text-direction marks. JavaScript's \s doesn't match them, so valid numbers were stored as invalid.

RuleStrip those marks first. Ambiguous numbers are flagged for the desk and never guessed, because a guessed country code can message a stranger.

A 28-minute Airtable outage lost a walk-in lead and two customer messages. I recovered them from the failed runs' raw payloads.

RuleRetries on every step whose failure loses a lead, and no intake branch may end before the lead reaches both systems.

About 3,100 outbound messages have been logged so far, from automations and from staff in the inbox. Meta lowers a number's quality rating when people block or report it. After more than 1,560 automated sends, the club's number is still rated GREEN, and all 48 templates are approved.

Evaluation and monitoring

Before a release

  • Eval harness: 33 cases (20 should reply, 10 should escalate, 3 the gate should stop), run against the real model. Decisions are scored automatically; reply wording I read myself.
  • Real-history replays: old prompt against new on real messages. For data jobs, old code against new on the same live data, expecting identical output apart from the intended change.
  • Deploy checks: back up, syntax-check every code node, read the workflow back byte-identical, connections unchanged, still active.
  • Adversarial review: many independent Claude reviewers on a risky change. For the assistant: 33 reviewers, 13 confirmed findings, all fixed before launch.

In production

  • Daily health check: every workflow active and its latest run healthy, API probes, template status, an urgent alert by e-mail.
  • Delivery status on every message.
  • Weekly report to the owner and finance lead: leads, conversion, messages and member activity.

Measuring the right thing

Both the member system's dashboard and the CRM said about 19% of leads became members. The member system only links a lead to a member when staff convert the lead record by hand, which they rarely do. Matching leads to members on e-mail and phone gave 40% across the club. The weekly report now shows both numbers side by side, with the method named.

A monitoring failure

The health check, its alerts and the weekly report all sent through one Gmail credential. When it expired, monitoring went silent for eight days, and I found a server outage from a screenshot of the hosting dashboard. A second alert channel outside the server is the open fix.

How I work

"I don't want people to feel they get spammed with wrong messages. That puts distrust into every message they get from the club, and they answer less in the future."From my notes, September 2026, before fixing the try-out follow-ups
  • I test on my own number, with a temporary every-minute schedule for headless runs, and restore the exact previous state afterwards.
  • I back up before every change and deploy through n8n's REST API, so a deploy can be reproduced and rolled back. Deploys, outage recovery and the monthly offer refresh each have a written runbook.
  • Every incident becomes a written rule, traced to the incident that caused it. The public list is in the repo.
  • I write for people who aren't technical. The owner, the finance lead and the front desk get plain reports and decide on anything that touches members.
  • I build with Claude Code as my pair. I make the design calls, write the tests, read the diffs, and answer for what runs in production.

What this project doesn't show

  • The assistant hasn't talked to real customers yet. The classifier has, on every website trial request.
  • Retrieval is small: an FAQ of about 350 lines in a cached prompt, plus a timetable. I haven't built embeddings or chunked search over large document sets.
  • Reply wording is judged by eye. The next step would be a judge calibrated on what staff change in drafts.
  • No voice channel yet.
  • The code lives in n8n Code nodes, with that sandbox's limits (300 seconds per run, no fetch). It is real JavaScript, but not a conventional repository with CI.
  • One client, built alone. My reviewers have been AI reviewers and the client, not other engineers.

One thing I would build at BluLang

Earned autonomy for BLUbot

Every new client's agent starts in draft mode. For each draft, log what staff did with it: sent as is, edited, or discarded, and how much they changed. Group the results by intent. When an intent such as opening hours or prices reaches, say, 95% sent unchanged over 50 drafts, it moves to auto-send for that client. An edit-back or a complaint moves it back to draft.

The hand-over line then comes from each client's own data instead of a guess at setup, and every staff edit becomes a test case for the next prompt change. I built the draft half of this for the gym; the measuring half is what I'd add.
